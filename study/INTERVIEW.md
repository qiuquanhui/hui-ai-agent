## 一、项目整体与选型（对应简历条目 1、2）

### Q1. 用一分钟介绍一下你这个项目。

**答**：这是一个从 0 到 1 手写的 AI 智能体应用：后端基于 Spring Boot 3 + Spring AI 接入通义千问，围绕一个"恋爱大师"对话应用逐步构建了提示词人设、责任链顾问、多存储对话记忆、RAG 私有知识库、7 件自定义工具，最后**不依赖任何 Agent 框架、用四个类的继承层次手写了一个 ReAct 模式的 Manus 智能体**，能自主完成"搜索地点→抓网页→下载图片→生成 PDF"这类多步任务；再通过 SSE 流式接口 + Vue3 前端 + 多阶段 Docker 构建部署到 Serverless 上线。

**可能追问**：项目里你一个人负责哪些部分？→ 全部，从骨架到部署（简历 14 条按时间线讲）。

### Q2. 你简历上写对比了五种调用大模型的方式，为什么最后选 Spring AI，而不是 LangChain4j 或者直接用官方 SDK？

**答**：
- **裸 HTTP / 官方 SDK**：能看清"调用大模型 = 发一段 JSON 收一段 JSON"的本质，但每个模型一套 API，换模型要改业务代码；
- **LangChain4j**：功能全面，但它自成体系，和 Spring 生态的整合（依赖注入、配置、自动装配）不如原生顺滑；
- **Spring AI**：ChatClient/Advisor/Tool/RAG 抽象统一，**换模型只换注入的 ChatModel、业务代码零改动**（项目里 DashScope 和 Ollama 实测互切过）；团队主力栈是 Spring，运维和招聘成本最低。
- 结论：小团队 + Spring 技术栈，Spring AI 是工程上最稳的选型；LangChain4j 我保留在知识面里做对比。

**可能追问**：那五种方式底层共同点是什么？→ 都是往一个 HTTPS 地址发 JSON（带 API Key 鉴权），拿回 JSON——框架做的只是"帮你写信封"。

### Q3. 这个项目里你觉得最有技术含量（或最难）的部分是什么？

**答**（准备两个，按面试官口味给）：**首选手写 Manus（简历 9）**——难点不在代码量而在控制权：要用 `withProxyToolCalls(true)` 关掉框架的自动工具执行，自己维护消息列表、自己写"思考-行动-观察"循环，还要用 TerminateTool + maxSteps 双保险防死循环；写完之后对 Agent 框架（LangChain4j 的 AiServices 等）的原理就"祛魅"了。**备选流式排查（简历 10）**——SSE 穿过 nginx 时被默认 `proxy_buffering` 攒成一坨，打字机效果消失，靠关缓冲 + `proxy_read_timeout` 放宽解决。

**可能追问**：手写完你理解了框架的什么？→ 所有 Agent 框架的本质都是这个循环 + 消息列表，差别只在封装程度。

### Q4. 如果重新做一遍或者继续迭代，你会改进什么？

**答**：① 记忆检索现在是"最近 N 条"，可升级为**按相关性检索的历史**（向量记忆）；② RAG 的向量库从内存版切 pgvector、并加命中率统计做评测（简历 7 的自然延伸）；③ Agent 的工具执行加**沙箱和白名单**（终端工具太危险）；④ 补齐可观测性——每次对话的 token 消耗、工具调用链路上报到监控。

## 二、ChatClient 与自动装配（对应条目 2、3）

### Q5. ChatModel 和 ChatClient 有什么区别？你项目里分别在哪用？

**答**：ChatModel 是**底层电话**——一问一答，每次调用都是"陌生人"；ChatClient 是**带秘书的电话**——Builder 出来后可以挂默认系统提示词（身份卡）、默认 Advisor（记忆/日志/鉴权）、工具箱，之后每次 `.prompt().user().call()` 自动带上这套配置。项目里阶段 2 的 Demo 直接注入 ChatModel 做对照实验，阶段 3 之后所有业务（LoveApp、Manus）都用 ChatClient。

**可能追问**：为什么不直接 new 一个 ChatClient？→ 它靠 Builder 构造并需要传入容器里的 ChatModel，交给 Spring 管理 + 构造器注入最干净。

### Q6. 你只加了一个 starter 依赖，代码里 @Resource ChatModel 就有值了，这是什么原理？

**答**：Spring Boot 自动装配——starter 里带着 AutoConfiguration 类，Spring Boot 启动时扫描 META-INF 里的装配清单，发现 classpath 有对应类 + 配置文件里有 `spring.ai.dashscope.api-key`，就构造好 DashScope 的 ChatModel/EmbeddingModel 并注册为 Bean，业务侧直接注入。所以"加依赖 + 写配置"两步就能用，零 new。

**可能追问**：有没有主动排除过自动装配？→ 有，阶段 6 排除了 `PgVectorStoreAutoConfiguration`——它和手写的 PgVectorStore Bean 冲突。

### Q7. 系统提示词你是怎么设计的？为什么这么设计？

**答**：四段式模板：**身份是谁（恋爱心理专家）→ 开场说什么（表明身份、告知可倾诉）→ 按情况分几类问（单身/恋爱/已婚三种状态各自问什么）→ 引导讲细节（事情经过、对方反应、自身想法）**。挂到 `defaultSystem` 后每次对话自动携带。这样设计的原因：只写"你是专家"一句，模型的追问方向漂移；把分类和追问策略写死在提示词里，多轮对话的风格和深度才稳定。

**可能追问**：defaultSystem 和每次 .system() 的区别？→ default 是默认值，单次 .system() 可覆盖；本项目人设固定用 default，结构化输出那次临时拼接覆盖过。

## 三、Advisor 责任链（对应条目 4）

### Q8. 讲讲你简历里写的"自定义 Advisor 责任链"，一个请求是怎么走完这条链的？

**答**：所有 Advisor 实现 CallAroundAdvisor/StreamAroundAdvisor，方法签名是 `aroundCall(请求, 链)`：**调用 `chain.nextAroundCall(req)` 就是放行**——请求传给下一个 Advisor，最终到大模型；不放行（也不抛异常）请求就"消失"。我挂了四位"老师"：权限校验 → 违禁词 → 记忆注入 → 日志。以一条消息为例：先对黑名单（权限），再查违禁词，然后记忆管理员把最近 10 条历史拼进 prompt，日志老师抄下最终请求，才发给模型；回信原路返回时再记日志、写记忆。

**可能追问**：这和 Spring MVC 的拦截器有什么异同？→ 同：都是责任链、都有"放行"语义；异：拦截器拦 HTTP 请求，Advisor 拦的是"发给大模型的 prompt"，作用在 AI 调用这一层。

### Q9. getOrder() 返回的数字是什么含义？你为什么把权限、违禁词排在记忆前面？

**答**：数字越小越先执行。官方记忆 Advisor 默认 `Integer.MIN_VALUE + 1000`，我把权限设为 `MIN_VALUE + 100`、违禁词 `+200`，**必须赶在记忆之前**——否则一条违规消息会先被写进会话记忆、然后才被拦截，脏数据留在笔记本里；先拦则违规请求根本到不了模型，也不产生任何 token 消耗。

**可能追问**：日志为什么排最后？→ 它要记录的是"过审后真正发出去的最终请求（含注入的记忆）"，排最靠后看到的最全。

### Q10. 拦截一个请求的正确姿势是什么？只实现 CallAroundAdvisor 会有什么问题？

**答**：正确姿势是**抛异常短路**（Assert 抛 IllegalArgumentException，测试里表现为用例红、接口里表现为 500）——不调 chain 又不抛异常，请求会像进了黑洞，那是 bug 不是拦截。只实现 CallAroundAdvisor 的问题：同步 `.call()` 正常，但流式 `.stream()` 走的是 StreamAroundAdvisor——顾问会**悄悄失效**，所以我的四个类两个接口都实现，流式分支里还用 MessageAggregator 把流聚齐后再记日志。

## 四、对话记忆（对应条目 5）

### Q11. 大模型本身是无状态的，你的多轮对话是怎么实现的？

**答**：本质是"**每次通话前把历史念给它听**"。MessageChatMemoryAdvisor 挂在链上：调用前调 `chatMemory.get(chatId, N)` 取最近 N 条历史拼进 prompt，调用后调 `add` 把本轮对话写回去。模型不用变，记忆全在应用侧。

**可能追问**：N 为什么是 10？→ 权衡：太小失忆（早期设 1 时隔句就忘），太大 prompt 冗长费钱；10 是对话场景的常用折中。

### Q12. chatId 在你项目里起什么作用？换一个会怎样？

**答**：chatId 是**笔记本编号**——同一个 chatId 用同一本记忆，AI 才记得住前文；换成新 chatId 等于开新本子，从头认识。我专门写过测试验证：A 本里说过"另一半叫 perper"，换 B 本再问就答不上来。前端每次新会话生成一个 UUID 当 chatId 传给后端实现隔离。

### Q13. 三种 ChatMemory 实现怎么做到"一行切换"？MySQL 版取最近 N 条为什么要倒序再 reverse？

**答**：三个类实现**同一个 ChatMemory 接口**（add/get/clear 三个方法），MessageChatMemoryAdvisor 只认接口不认实现——构造 LoveApp 时换一行 new，就是策略模式的典型收益。MySQL 取数细节：表里自增 id 天然记录先后，`ORDER BY id DESC LIMIT N` 先拿**最新的 N 条**（LIMIT 必须配 ORDER BY 才有意义），但结果是"新在前"，必须 `Collections.reverse()` 翻回"旧在前"——AI 按正常聊天顺序读才通顺。

**可能追问**：为什么接口方法长这样？→ add(会话, 消息列表)/get(会话, N)/clear(会话)，恰好覆盖"记、忆、忘"三个动作，任何存储都能映射。

### Q14. 文件版记忆为什么用 Kryo，而不是 JSON 或 Java 自带序列化？

**答**：Message 列表要落盘就得序列化。Java 自带 ObjectOutputStream 产物**又大又慢**还有反序列化安全漏洞前科；JSON 是文本、人能读、跨语言，但体积大；Kryo 是二进制、只在 Java 内部存取，**小几倍快几十倍**——"对外交换用 JSON，自己家里存取用 Kryo"。代价是 .kryo 文件不可读、换语言环境不可移植。

## 五、RAG 检索增强（对应条目 7）

### Q15. 什么是 RAG？为什么用它而不是微调？

**答**：RAG = 检索增强生成，**开卷考试**：答题前先从私有知识库里检索相关片段、抄在题目旁边，模型照着答。用它而不是微调的原因：① 微调贵、周期长，知识更新要重训；② RAG 只需换文档，几分钟生效；③ 回答**可溯源**（能指出依据哪份文档），幻觉可控。模型负责"读资料组织语言"，资料由程序负责递。

**可能追问**：什么场景该微调？→ 需要改变模型的"风格/能力"而非"知识"时（如让它学会某种固定格式推理），知识注入优先 RAG。

### Q16. 描述你 RAG 的完整流水线。

**答**：四步——**① 离题向量**（问句也过 EmbeddingModel 变向量）→ **② 检索**（向量库里比距离，取最相关的 topK 张）→ **③ 增强**（把卡片正文拼进 prompt："参考以下资料……请回答……"）→ **④ 生成**（模型照资料作答）。工程上分两个时段：启动时（@Bean 里）做卡片入柜；提问时由 QuestionAnswerAdvisor 自动完成①②③。

**可能追问**：RAG 在 Spring AI 里是什么身份？→ 本质就是一个 Advisor，和日志/鉴权顾问站同一条链，干的活是"递资料"。

### Q17. Embedding 到底是什么？为什么"以意思找意思"比关键词匹配强？

**答**：Embedding 是把文本翻译成 1536 维向量——相当于给每句话标一个 GPS 坐标，且**意思越近坐标越近**。检索就是"问题坐标 vs 卡片坐标"比距离。关键词匹配是死板配字：用户问"家务分工闹矛盾"，文档写"夫妻责任分配冲突"，一个字都对不上但意思相同——向量距离却能识别这种语义等价。这是 RAG 检索质量的根基。

### Q18. 查询重写你是怎么实现的？为什么强调中文模板？

**答**：缘由是用户口语（"我老婆天天跟我吵家务咋整啊顺便推个课呗"）整体做向量会被口水词带偏。实现：**用大模型先改写，再拿干净问题去检索**——本质两次模型调用：第一次是 RewriteQueryTransformer（Spring AI 官方组件）+ 我自定义的中文 PromptTemplate（含 {query}/{target} 两个占位符，builder 会校验不能删），把口语整理成"已婚夫妻家务分工矛盾如何解决"；第二次才是正常 RAG。中文模板是踩坑换来的：官方默认模板是英文且没要求保持语言，中文问题常被翻译成英文回来——可我的卡片是中文的，英文问题对中文卡片，向量方向全偏，检索质量暴跌。

**可能追问**：为什么占位符在模板里？→ 框架运行时填充的填空位：{query} 填用户原话，{target} 由 targetSearchSystem("向量数据库") 填入，告诉模型"改写是为了去哪查"。

### Q19. 你做的 status 标签过滤、similarityThreshold、topK 分别解决什么问题？

**答**：三个检索质量旋钮——**status 过滤**（FilterExpressionBuilder 的 eq，相当于 WHERE status='已婚'）：知识库按单身/恋爱/已婚混放，不过滤会串味；**similarityThreshold(0.5)**：相似度低于 0.5 的卡片宁可不带——带一张不相关的比不带更糟，模型会被带偏；**topK(3)**：最多带 3 张，多了 prompt 冗长费钱。配套还有空结果兜底：`allowEmptyContext(false)` + 固定话术，没翻到书就老实说"只能回答恋爱相关的问题"，不让模型瞎编。

**可能追问**：标签从哪来？→ 入库时贴的：DocumentReaderConfig 的 withAdditionalMetadata("status", 文件名前两字)——所以文件起名要守约定。

### Q20. RAG 这块你踩过什么印象深的坑？

**答**（备三个）：① **灵积 Embedding 单次最多 25 条**——入库一次性 add 全部文档直接报错，改成 batchSize=10 分批插入；② **查询重写的英文模板问题**（见 Q18）；③ **切分粒度**：卡片太长检索不准、太短语义破碎——Markdown 靠 `---` 分隔线切，保底用 TokenTextSplitter（默认 200 token/段）。

## 六、工具调用（对应条目 8）

### Q21. AI 是怎么"使用"你的工具的？谁在真正执行？安全性怎么考虑？

**答**：流程是：**AI 动嘴，我的程序动手**——`.tools(allTools)` 把 7 件工具的说明书（@Tool/@ToolParam 的 description）随 prompt 发给模型；模型不返回文字而是返回"工具调用指令"（工具名 + JSON 参数）；框架在我的 JVM 里**反射执行**对应方法；结果作为 ToolResponseMessage 回喂给模型，它再组织成人话。安全性核心正在于此：模型永远只发指令、永远碰不到我的电脑，执行权、参数校验、文件目录边界（统一限制在 tmp/ 下）都在程序侧；最危险的终端工具仅限演示，生产要加白名单/沙箱。

### Q22. @Tool 的 description 有什么讲究？写不好会怎样？

**答**：description 是发给 AI 的**菜单条目**——模型全靠它决定"什么时候用、用哪件"。写得含糊（如只写 "search"），多工具场景下会挑错或该用不用。经验：写清"能干什么 + 什么时候用"，参数用 @ToolParam 逐一说明；TerminateTool 的说明书甚至写明"任务完成或无法继续时调用"——**它的功能就长在说明书里**，这直接决定 Agent 能否正确收工。这也解释了为什么工具方法要返回字符串、异常也 catch 成字符串：错误信息同样是模型决策的输入。

### Q23. 7 个工具是怎么统一交给框架的？ToolCallbacks.from 做了什么？

**答**：ToolRegistration 配置类里 @Bean 一个 `ToolCallback[]`：7 个工具类都是**普通对象（new 出来的，不是 Spring Bean）**，`ToolCallbacks.from(...)` 把它们**适配/翻译**成框架统一的 ToolCallback 数组——从此模型眼里 7 件工具长一个样（一份说明书 + 一个可调用方法）。一个细节：WebSearchTool 要 SearchAPI 钥匙，但它不是 Spring 零件拿不到 @Value，所以由注册类读 `@Value("${search-api.api-key}")` 后**构造器手动传入**。

## 七、手写 ReAct 智能体（对应条目 9）

### Q24. 为什么手写 Agent 而不用现成框架？讲讲 ReAct 在你项目里的循环。

**答**：目的有二——① 不被框架黑盒绑架，理解 Agent 的最小本质；② 按需定制（自研收工信号、逐步播报）。ReAct = Reason + Act 交替：`run()` 是 for 循环（最多 20 步），每圈 `step() = think() + act()`——think 把**全部历史消息 + 7 件工具菜单**发给模型，看它返回的工具指令单：挑了工具就 act（真正执行、结果整包写回消息列表），没挑说明只想说话；act 里检查是否调用了 doTerminate，调了就把状态灯置 FINISHED、循环结束。**带着全部历史重新想每一圈**，就是"它会连续做事"的全部秘密。

### Q25. withProxyToolCalls(true) 是干嘛的？不设会怎样？

**答**：它把框架的"自动工具执行"关掉，换成**代理模式**——模型发来的工具指令不由框架悄悄执行，而是原样交还给我的 act()，由我调 ToolCallingManager.executeToolCalls 手动执行、自己维护消息列表。不设的话：框架替我执行并把结果塞回对话，我**插不进任何自己的逻辑**——检查"是否该收工"、把每步结果推给前端（SSE 播报）都做不了，"思考-行动-观察"的节奏就不在我手里。一句话：写应用让框架代劳省心，写 Agent 必须拿回控制权。

### Q26. 怎么防止 Agent 陷入死循环？

**答**：**双保险**——① `maxSteps`（设 20）：硬上限，像"最多磨蹭 20 分钟必须交作业"，每一步都在真实调模型花钱，必须有闸；② **TerminateTool 软信号**：下一步提醒词里明确告诉模型"任务完成或无法继续就调用 terminate"，act() 检测到该工具被调用就置 FINISHED 正常收工。两道防线互补：模型忘了喊停，maxSteps 兜底；任务简单时也能一步就停不浪费步数。

### Q27. 为什么 /manus/chat 每次请求都要 new 一个 HuiManus，而 LoveApp 的 ChatClient 可以全局单例？

**答**：**有状态 vs 无状态**。HuiManus 实例体内装着消息列表（工作记忆）和状态灯——单例复用会导致 A 用户任务的上下文串进 B 的会话，而且状态灯没回 IDLE 时第二个任务直接抛 "Cannot run agent from state: RUNNING"；所以控制器里每次 `new HuiManus(allTools, chatModel)`。ChatClient 相反是无状态的（每次调用的上下文由 chatId 参数注入，记忆存在外部 ChatMemory 里），可以全局共享——这个对比其实帮我理解了"状态到底存在对象里还是存在外部存储里"两种设计。

## 八、流式输出与前端（对应条目 10、12）

### Q28. SSE 和 WebSocket 怎么选？Flux 和 SseEmitter 两种实现有什么差异？

**答**：场景是"服务端单向推送、HTTP 即可"——SSE 够用且更轻（纯 HTTP、自动重连、穿透代理简单）；WebSocket 是双向全双工，适合聊天室多人互推、协同编辑这类双向场景，我们不需要。两种实现殊途同归：**Flux** 声明式、链路干净，`.stream()` 一词从同步切流式；**SseEmitter** 命令式、控制粒度细——能显式掌握 send/complete 的时机，**Manus 的逐步播报正是要"每干完一步手动 send 一次"**，所以 Manus 用的 SseEmitter，配合 CompletableFuture.runAsync 把循环挪到异步线程，HTTP 线程挂上喇叭就返回，不阻塞容器线程池。

**可能追问**：部署后打字机失效过吗？→ 有，nginx 默认 `proxy_buffering on` 会把流攒成一坨——关缓冲（proxy_buffering off、Connection ""、read_timeout 放宽）后恢复。

### Q29. 前端为什么不用浏览器自带的 EventSource，而用 fetch 手写 SSE 解析？半包问题怎么处理？

**答**：EventSource 有两个硬伤——感知不到"流的正常结束"（onDone 时机拿不到，无法解锁输入框），也不能中途 abort（做不了"停止生成"）。所以用 fetch + AbortController 手写：`response.body.getReader()` 逐块读，**按 `\n\n` 切分事件**——关键在切完把最后一段 `pop` 回 buffer：网络分帧不保证按事件边界到货，最后一段可能是半截事件，必须留在托盘里等下一帧拼上再判完整。这个"半包粘包"处理是所有流式解析的通用范式。

## 九、工程与部署（对应条目 13、14）

### Q30. 讲讲你的密钥安全方案和 Docker 多阶段构建为什么能瘦身。

**答**：**密钥三层隔离**——① 公开配置（application.yml / prod.yml）进 git，只放非敏感项；② 真实密钥放 application-local.yml，被 .gitignore 挡住不进仓库、被 .dockerignore 挡住不进镜像（Docker COPY 不看 .gitignore，必须单独挡）；③ 生产用环境变量注入（SPRING_AI_DASHSCOPE_API_KEY 等，点变下划线全大写），环境变量优先级高于 jar 内所有配置文件——同一个 jar 插不同钥匙随处跑。**多阶段构建瘦身**——第一阶段用 maven + JDK 镜像编译打出 jar；第二阶段换纯净的 JRE 镜像只 COPY jar 进去：Maven、源码、编译工具全部留在第一阶段不进最终镜像，体积从 1GB+ 降到几百 MB，Serverless 冷启动显著变快；再加 `-XX:MaxRAMPercentage=75.0` 让堆内存按容器限额自适应，避免小内存实例被 JVM 撑爆。

**可能追问**：为什么不把 local.yml 打进镜像里方便点？→ 镜像会进镜像仓库、被分发——等于把家门钥匙印在照片上发朋友圈；环境变量由平台托管、可轮换，才是正解。
